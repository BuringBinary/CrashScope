## 1. 执行摘要

这次现场数据足以还原一条比“游戏用了 14.85 GiB”更完整的故障链：

1. **CrashScope 开始记录时，系统早已处于危险状态。** 三角洲旧进程 PID 11248 创建于 19:11:52，记录器到 21:08:18 才启动；首个五秒样本已经是 `38.002 / 38.945 GiB`、97.58%。因此本次数据能看到最后 23 分钟，却看不到前约 1 小时 56 分钟的增长起点。
2. **系统持续受提交内存上限约束，而不是物理 RAM 或独显显存先耗尽。** 278 个五秒样本中，276 个达到 90%，250 个达到 95%，183 个达到 98%，29 个达到 99%。一秒遥测在 21:31:18 只剩约 4.6 MiB 提交余量，但仍有约 4.59 GiB 物理 RAM 可用。
3. **游戏资源存在明显的“释放—重建”周期。** 21:27:54 前后，系统提交、游戏进程 GPU dedicated 记账和适配器级显存同时下降；随后三者又一起增长。276 个重叠五秒样本中，系统提交与游戏 GPU dedicated 的 Pearson 相关系数为 0.9793，游戏 GPU dedicated 与独显适配器已用显存的相关系数为 0.9976。相关性不能单独证明因果，但表明本次大幅波动主要跟随游戏图形/资源生命周期，而不是磁盘或 CPU。
4. **最终退出前，图形活动先停止，进程提交后释放。** 21:31:14 独显负载仍为 89%；21:31:15 降到 7%，游戏最后一个 GPU engine 记录也在这一秒；21:31:18 提交达到 99.988%；21:31:22 前台切离游戏，同时约 7 GiB 提交余量和约 6.87 GiB 独显驻留显存被释放。
5. **旧 PID 没有干净完成资源回收，是重试连续耗尽的核心。** 21:32:13 和 21:34:50 的 Windows 事件 2004 仍把完全相同的 8.380 GiB 提交记在旧 PID 11248 上；该条目的句柄数为 0、版本为 0.0.0.0，说明它已不是一个健康运行中的正常游戏实例，至少处于终止中、不可查询或遗留记账状态。新 PID 33844、36452 分别叠加 5.920、7.072 GiB，令旧新进程合计再次达到 14.30 和 15.45 GiB。
6. **磁盘、温度、GPU 驱动重置和 WHEA 都不是主要候选。** 磁盘读写延迟绝大多数低于 1 ms、队列 p95 为 0；RX 9070 XT 核心/显存/热点最高 55/68/78°C，独显显存最低仍有 6.455 GiB 空闲；同期没有 Display 4101、WHEA、Kernel-Power 41 或相关应用崩溃 1000/1001。
7. **GameDVR 是可能的最后触发因素或受害者，但不是根因。** 21:31:14，Windows 记录 GameDVR/BcastDVR 服务 30 秒启动超时和 DCOM 1053；21:31:15 又出现 GameBar、RuntimeBroker 与数个服务进程的启动突发，恰逢游戏 GPU 活动消失。但此时系统已经长期贴近提交上限，现有一秒粒度无法判断 GameDVR 是触发最后一次分配失败，还是在全局资源耗尽下跟着失败。
8. **CrashScope 本次“数据可用”，但不能判为完整验收通过。** 采样时钟和 JSONL 完整性很好，内存、适配器 GPU、存储和前台链路有效；但 ETW GPU 接收 1.916 亿事件却写入 0 条，Power ETW 因非管理员权限失败，CPU 温度/频率缺失，进程快照没有提交/工作集，按进程 GPU 又丢失 adapter/LUID，且没有 DWM 状态文件。决定性进程归因来自事后查询 Windows 事件，而不是会话自身。

本报告不重新扩展 ACE 调查。已经确认本次 ACE 后半段是非正常重启后的预启动静默模式，不是反作弊判罚；详细证据见关联报告。

### 5.2 Windows 2004 的系统构成

21:30:48 的原始 XML 给出：

- 系统提交：39.022/39.115 GiB，99.764%。
- 普通进程提交合计：29.621 GiB。
- PID 11248：14.853 GiB，约占普通进程提交的一半。
- 分页池：1.239 GiB；非分页池：1.854 GiB。
- 物理内存：18.480/23.115 GiB，仍有约 4.64 GiB 未占用。
- 进程数：311。

这解释了为什么应用把错误描述为“物理内存不足”，但 Windows 的直接诊断是虚拟内存/提交上限耗尽。第一次事件时 RAM 并未耗尽；到重试事件，物理使用上升到 22.445 和 22.382 GiB，说明新进程启动又让大量页面驻留，RAM 和 commit 随后同时接近极限。

### 6.2 游戏 GPU 活动早于进程资源完全释放而消失

- 游戏 GPU 3D engine 最后一条：21:31:15.559。
- 游戏进程 GPU memory 最后一条：21:31:19.574。
- 游戏前台结束：21:31:22.573。
- 系统提交与适配器显存大幅释放：21:31:22–21:31:24。
- 旧 PID 的 8.380 GiB 提交仍被 21:32 和 21:34 的 Windows 事件列出。

因此可以直接回答原验证问题：**游戏 GPU 活动消失早于旧进程提交记账完全消失。** 这是“图形上下文/显存资源先退场，但进程基础提交或终止清理残留”的证据链。

### 6.3 按进程 GPU 口径存在适配器混合

会话里的按进程 dedicated 峰值：

- `DeltaForceClient-Win64-Shipping`：6.774 GiB。
- `GameViewerServer`：固定约 7.706 GiB。
- `dwm`：约 2.123 GiB。

这些数不能相加后当作 RX 9070 XT 的物理显存。驱动清单同时存在：

- RX 9070 XT；
- Ryzen 集成显卡；
- `GameViewer Virtual Display Adapter`。

当前 `GpuMemoryTracker` 把 `GPU Process Memory` 的所有 instance 按 PID 相加，但不保存 instance 中的 adapter LUID/physical adapter/segment 身份。`GpuEngineTracker` 也把同 PID、同 engine type 的多个 instance 相加，所以出现了 164.60% 的游戏 3D 值和 167.64% 的适配器 D3D 3D 原始峰值。

退出后更能看出口径问题：21:31:29 适配器实际已用显存只有 2.975 GiB，而 `GameViewerServer` 与 `dwm` 的进程 dedicated 记账相加已经远大于此值。它们可能属于不同适配器、虚拟适配器、提交而非驻留口径，或包含共享资源重复记账。产品必须按 adapter/LUID 展示，不能把当前汇总字段命名为“实际占用的独显物理显存”。

### 6.4 DWM 与显示状态

- `dwm.exe` PID 1696 出现在全部 46 个进程快照中，GPU memory 也覆盖全部 278 个五秒样本。
- 只有一个 2560×1440 物理显示器基线；没有拓扑变化。
- 会话为本地 console，不是远程会话。
- 没有 Display 4101 驱动重置事件。

这些是 DWM 持续存活的间接证据。但现场目录没有 `dwm-state.jsonl`；当前源码按设计应写一个 composition baseline，因此需要单独复现包版本、运行路径和构建身份，不能把缺文件解释成“DWM 没变化”。

- 提交占比与读/写延迟的相关系数分别为 -0.0281、-0.0257。
- 提交占比与队列深度为 -0.1171。
- 提交占比与 Disk Time 为 -0.3267；大幅资源释放/重载时反而出现部分 I/O 峰值。
- `abs(提交变化)` 与 Disk Time 为 0.3855，说明资源切换伴随 I/O，但没有伴随高延迟或持续队列。

最终阶段 Disk Time 曾到 33.85%，释放后仍约 23%，但读写延迟保持约 0.3–0.6/0.08–0.13 ms，队列 0–2。结论是**磁盘有活动，但没有磁盘排队或页面文件 I/O 卡死的证据**。

SMART 健康和温度完全缺失；collector health 已诚实说明 Windows I/O counters 不提供这些值，LHM 也没有返回磁盘传感器。这是覆盖缺口，不是“磁盘健康正常”的证据。

### 7.3 前台、进程和上下文

- 游戏前台累计 1,361.016 秒，占遥测覆盖的 97.99%。
- 进程数平均 311.4，范围 310–317；这是一个很重的真实桌面环境。
- 首/末快照都有 59 个 `msedgewebview2`、16 个 `ShunCode`、9 个 `QQ`、7 个 `msedge`、6 个 `browser`。
- PID 11248 出现在全部 46 个快照中；会话内没有它的 stop 事件。
- `SGuard64`、`SGuardSvc64`、ACE tray、Wegame 和 GameViewer 组件也持续存在。

这些后台程序共同占用资源，但会话没有记录它们的 Private Bytes、Commit Size 或 Working Set。除事件 2004 的前三名外，不能按进程给出完整提交排名，也不能把 59 个 WebView2 的数量直接换算成内存占用。

## 8. Windows 事件关联

21:00–21:36 的 System/Application 警告和错误主要分为四类：

1. 三次 Resource-Exhaustion-Detector 2004；
2. 21:31:14 的 GameDVR/BcastDVR 服务超时和 DCOM 1053；
3. 游戏重试时 ACE 文件系统筛选器的 FilterManager 11；
4. 21:08:19 CrashScope Desktop PID 32848 初始化时产生的 Perflib 1008/1023 与 usbperf 2001。

显式检查结果：

- Display 4101：0。
- WHEA-Logger：0。
- Kernel-Power 41：0（本窗口截至 21:36；后续非正常重启不在本段根因分析内）。
- 含 DeltaForce/CrashScope/DWM/GameViewer/AMD 的 Application Error/Windows Error Reporting 1000/1001：0。

所以这不像 GPU 驱动 TDR、WHEA 硬件错误或有转储的标准应用崩溃。更符合应用在分配失败后自行报错/退出，或进程进入异常终止清理，而 Windows 只留下资源耗尽事件。

CrashScope 启动引发的 10 条 Perflib/usbperf 事件由事件 XML 的 `Execution ProcessID=32848` 直接确认。它们涉及 .NETFramework、ESENT、RDS、MSDTC、ReadyBoost、RemoteAccess、USB 和 WMI 计数器，其中多数与本次实际使用的 GPU/PhysicalDisk 指标无关。说明当前性能计数器初始化会触碰或加载系统中损坏/不可用的 provider，造成事件日志噪声；应减少全局探测并把具体 counter 打开失败写入 collector health。

## 9. 最可能的故障机制

### 9.1 高置信主链

1. 长时间运行的 PID 11248 与大量桌面后台共同把系统提交维持在 38–39 GiB，提交上限约 39.1 GiB。
2. 游戏在场景/资源切换中反复释放并重建图形资源；提交与显存几乎同步变化。
3. 最终阶段可用提交降到只有几 MiB，Windows 2004 将 14.853 GiB 直接归因给游戏。
4. GameDVR/覆盖层相关服务在临界时刻尝试启动或失败，可能提供了最后一次额外分配压力。
5. 游戏 GPU 活动停止；随后图形资源释放，系统提交和适配器显存同时下降约 6–7 GiB。
6. 旧 PID 仍留下 8.380 GiB 提交记账；快速重试的新实例与旧记账重叠，再次触顶。

### 9.2 “14.853 → 8.380 GiB”意味着什么

第一次事件到重试事件，旧 PID 的提交减少约 6.473 GiB；同期游戏 GPU dedicated 约 6.77 GiB 消失，适配器级显存约释放 6.87 GiB。三个量级接近，支持如下解释：

- 约 6–7 GiB 是随图形上下文/资源退出而释放的那部分；
- 旧进程仍有约 8.38 GiB 基础提交没有完成回收；
- 重试不是从干净基线开始，而是在残留之上重新分配。

这仍是“最符合数据的机制”，不是分配级证明。没有进程内存 map、堆快照、驱动 allocation trace 或退出转储，不能断言这 8.38 GiB 属于哪一类堆，也不能区分应用线程卡在退出、驱动/内核引用延迟清理和 Resource Exhaustion Detector 的终止中记账。

### 9.3 次要或低置信因素

- **GameDVR/Game Bar：中低置信。** 时间高度接近，但可能是受害者。
- **CrashScope：不是主源，但可能提前触顶。** 事件 2004 证明其提交低于 0.663 GiB；然而系统只剩几 MiB 时，任何记录器/ETW 缓冲都有边际影响。
- **其他桌面程序：贡献背景负载。** WebView2 单进程达到约 1.04–1.06 GiB，Explorer 约 0.66 GiB；其余缺少进程提交字段。
- **内核池/ETW：有开销但非已证主因。** 21:30:48 非分页池为 1.854 GiB，`EtwB` 标签约 0.166 GiB；`EtwB` 是全系统 ETW 合计，不能全部归因 CrashScope。

## 10. 证据等级与未回答问题

### 10.1 直接证据

- 系统提交长期 95–99% 及一秒峰值 99.988%。
- 首次事件时仍有数 GiB 物理 RAM，独显仍有 6.455 GiB 空闲。
- Windows 2004 对三个游戏 PID 的提交量、创建时间、句柄数和系统内存构成。
- 游戏 GPU 活动在 21:31:15 消失，前台在 21:31:22 切走，提交/显存在同一时间段释放。
- 旧 PID 的 8.380 GiB 在两次重试事件中完全不变，新 PID 与它重叠。
- CPU 未总体饱和，磁盘延迟/队列正常，GPU 温度正常。
- 没有 Display 4101、WHEA、同期 Kernel-Power 41 和相关 1000/1001。

### 10.2 有数据支撑的推断

- 总提交的大幅波动主要由游戏图形/资源生命周期驱动。
- 首次退出释放的是图形相关大块资源，而旧 PID 的基础提交未完成清理。
- 重试失败主要由“旧记账残留 + 新实例重新分配”造成。
- GameDVR 启动突发可能是最后触发因素或资源耗尽的连带失败。

### 10.3 现有数据不能回答

- PID 11248 从 19:11 到 21:08 的增长曲线，是否存在单调泄漏。
- 哪个具体分配调用失败、游戏退出码、线程/堆/模块级归因。
- 旧 PID 8.38 GiB 为什么持续：应用退出卡死、驱动引用、内核清理延迟还是事件记账语义。
- 如果不运行 CrashScope，故障会推迟多久或是否发生。
- CPU 是否曾热节流，因为温度和有效频率缺失。
- 页面文件当时的准确配置、最大值和扩展受限原因。
- ETW 的 OS-level 丢事件数量；collector 只记录 handoff drop。
- 每个进程 GPU 记账属于 RX 9070 XT、集显还是 GameViewer 虚拟适配器。
- `dwm-state.jsonl` 缺失是包版本差异、初始化路径还是运行缺陷。

## 12. 产品修复优先级

### P0：下一次游戏采集前

1. **停用或严格收窄 DxgKrnl ETW。** 禁止 `Verbose + ulong.MaxValue`；先用离线可验证事件集合，记录 OS lost events、缓冲大小、事件率和匹配率。游戏安全模式下默认关闭实时 DxgKrnl。
2. **增加按进程内存与生命周期。** 至少采集 PID、创建时间、Private Bytes/Commit Size、Working Set、句柄数、退出状态；2–5 秒采样，并检测“GPU activity 消失但进程 commit 不释放”和同名 PID 代际重叠。
3. **原生捕获 Resource-Exhaustion-Detector 2004。** 保存完整 `UserData`：系统 commit、process commit、物理使用、池使用、top process、CreationTime、HandleCount；不要等事后人工查询。
4. **GPU 计数器按 adapter/LUID 分层。** 解析 instance 中的 LUID、physical adapter、engine/segment；映射 RX 9070 XT、集显和 GameViewer 虚拟适配器。不得把跨适配器汇总值当独显显存或普通 0–100% 百分比。
5. **提交压力自保护。** 在 90/95/98% 分级告警；达到 95% 自动降低采样/关闭 ETW，达到 98% 只保留系统 commit、适配器温度和关键 Windows 事件，避免成为最后一根稻草。

### P1：诊断可信度

6. **采集自身开销。** 每 5 秒记录 CrashScope Desktop/Agent/Service 的 CPU、Commit、Private Bytes、Working Set，以及 ETW buffer/事件率，才能做反事实边界。
7. **为稀疏流写 heartbeat/zero sample。** `gpu-engines.jsonl` 需区分“确实空闲”“collector 调用失败”“无可用 counter”，否则 8 秒空白只能靠旁路推断。
8. **修复/验证 DWM baseline。** 每次会话必须有 `dwm-state.jsonl` baseline，collector health 中增加 DWM 状态；包验收检查必需文件集合。
9. **CPU fallback 和权限预检。** 为 Ryzen 温度/有效频率增加可靠来源；启动前明确显示 Power ETW 需要管理员，W3 若要求完整 ETW 应先断言 `elevated=true`。
10. **页面文件现场快照。** 记录 AutomaticManagedPagefile、每卷当前/峰值/最大配置、卷空闲空间和 commit-limit 变化事件。
11. **降低 Perflib 初始化噪声。** 避免触发不相关 provider；把每个 counter 打开失败关联到具体 collector，而不是向 Application 日志一次写入十条系统 provider 错误。

### P2：稳定性和可追溯性

12. **完成 30–60 分钟和 2–4 小时双阶段测试。** 分别做空闲基线、普通桌面、单游戏、游戏加后台四组，对比自身 CPU/内存和 ETW 事件率。
13. **统一会话身份。** 目录名、Journal、RPC、incident bundle 使用同一个 Session ID，并把完整构建身份写进会话，不只保存程序集版本。
14. **自动生成事故窗口。** 一旦 commit 达到 95% 或出现 2004，自动延长采集并冻结前后 5–10 分钟尾部；不要在第一次退出后立即停止而丢掉重试链。

## 13. 下一轮最小验证设计

为了区分“游戏自然高占用”“单实例增长”和“退出残留”，下一轮不必先做危险的全量 ETW：

1. 重启后确认没有旧游戏 PID；记录系统 commit 和页面文件基线。
2. CrashScope 使用安全模式，只开系统 commit、适配器 GPU、存储、前台、按进程 commit/lifecycle 和 Windows 2004。
3. 从启动器之前开始录，覆盖游戏冷启动、进入对局、退出到桌面、等待 3 分钟、再启动一次。
4. 关键验收：旧 PID 的 commit 是否在 30 秒内归零；新 PID 启动时是否存在旧 PID；commit 与 VRAM 是否仍同步；退出后是否保留句柄数 0、固定 8 GiB 级条目。
5. 单独做 30–60 分钟无游戏基线，确认 CrashScope 自身开销和事件率；在这一步通过前不要恢复全量 DxgKrnl ETW。
