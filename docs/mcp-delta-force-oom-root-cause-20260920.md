# 三角洲闪退与内存耗尽：游戏日志级根因复核

分析日期：2026-09-20（UTC+8）
事故窗口：2026-09-18 21:30–21:35；对应用户提供的“可用物理内存不足”截图及当晚 CrashScope 0.9.2 采集会话。

## 1. 结论

**本次已确认发生了真实内存分配失败（OOM），不是仅凭弹窗推测。最符合现有证据的链条是：系统提交内存长期接近上限 → 游戏 D3D12 堆申请失败并退出 → 旧游戏 PID 的提交记账仍未消失 → 新实例与旧记账重叠，两次重试进一步发生普通内存分配失败。**

但必须区分两个问题：

- **为什么闪退：已定位到分配失败。** 首次是 D3D12 `CreateHeap` 返回 `E_OUTOFMEMORY`；重试是 64 KiB、560 KiB 的分配失败。
- **谁的哪段代码发生了持续内存泄漏：尚未定位。** 现有证据确认高提交量、退出后的旧 PID 记账残留和重试重叠，但没有足够的进程级长期曲线、分配堆快照或符号化调用栈来证明具体泄漏点。

**不能将“Out of video memory”直接解释成 RX 9070 XT 的 16 GB 显存已经用满，也不能把用户截图里的“物理内存不足”当作精确的 Windows 失败分类。** 首次故障时系统 commit 几乎耗尽，独显显存预算与传感器却均显示仍有余量。

## 2. 本轮新增的关键证据：游戏自身日志

通过卸载注册信息定位到游戏安装目录，在 `DeltaForce/Saved/Logs/` 找到当晚首次退出及两次重试的原始日志。日志不是直接可搜索的普通明文；按其字节编码还原后，只提取与内存和退出相关的内容，保留原文件哈希与还原后的行号。

本轮检查了四份日志，其中前三份与 OOM 链条有关：

- `DeltaForce-backup-2026.09.18-13.31.21.log`
- `DeltaForce-backup-2026.09.18-13.32.57.log`
- `DeltaForce-backup-2026.09.18-13.35.28.log`
- `DeltaForce-backup-2026.09.18-13.41.18.log`（后续阶段，不混入首次内存事故）

文件名后缀与日志内容时间相差八小时。本文用与系统事件及 CrashScope 对齐的日志内容时间。截图本身没有可核对的发生时间，不能仅凭图片断定它属于三次中的哪一次。

以下引用中的行号为还原后日志行号。仓库内摘录位于 `.mcp-probes/delta-memory-cause-20260920/`，没有复制完整游戏日志或上传到第三方。

### 2.1 首次退出：D3D12 创建堆失败

第一份日志 671947–671949 行，时间 **21:31:14.455**：

```text
LogD3D12RHI: Error:
Adapter->GetD3DDevice()->CreateHeap(&Desc, IID_PPV_ARGS(&Heap)) failed
... D3D12Allocation.cpp:4192
with error E_OUTOFMEMORY
```

随后 671993–671995 行，**21:31:16.093**：

```text
Memory Info from frame ID 1794064:
Budget: 15416.53 MB
Used:    6864.32 MB
```

672007–672008 行：

```text
Fatal error: [File:Unknown] [Line: 941]
Out of video memory trying to allocate a rendering resource
```

21:31:21.649 记录工作线程崩溃；21:31:21.671 记录 `FPlatformMisc::RequestExit(1)`。

**含义**：这不是只有一个预警弹窗，而是游戏渲染后端已经出现致命分配错误。`D3D12Allocation.cpp:4192` 是报错/申请失败位置，不等于内存泄漏源位置；没有拿到该构建的完整堆描述和调用栈，不能断言具体是哪个纹理、资源缓存或驱动对象泄漏。

### 2.2 第一次重试：64 KiB 都无法分配

第二份日志 44649–44658 行，**21:32:14.007**：

```text
Freeing 33554432 bytes from backup pool to handle out of memory.
AvailablePhysical 632877056
UsedVirtual       6468804608
AvailablePageFile  4935680
TotalPageFile      41999097856
```

随后 **21:32:57.626**，44676–44677 行：

```text

```

这里 `AvailablePageFile` 约 **4.71 MiB**。该 Windows 内存统计字段表达的是可提交余量相关信息，不是 C 盘剩余空间；`TotalPageFile` 也不能解释成“pagefile.sys 文件大小为 39 GiB”。

### 2.3 第二次重试：560 KiB 分配再次失败

第三份日志，**21:34:50.488**：

```text
Freeing 33554432 bytes from backup pool to handle out of memory.
AvailablePhysical 790405120
UsedVirtual       7623618560
AvailablePageFile  3383296
TotalPageFile      41999097856
```

**21:35:28.873**，44027–44028 行：


可提交余量相关字段只剩约 **3.23 MiB**。这些瞬时记录不保证某个时刻任何小请求都能成功：分配器可能按更大粒度提交，其他线程/进程也在并发分配。

这两次都记录了释放 32 MiB 备用池的 OOM 处理行为，随后仍进入 Fatal Error，说明不只是显存提示文案含糊，普通内存申请也已经失败。

## 4. 到底是物理内存、显存，还是提交内存？

### 4.1 首次故障的最强解释：系统提交余量不足

机器可用物理内存总量约 23.1 GiB（24 GB 级配置）。Windows 的 commit 是系统承诺为内存分配提供后备存储的总量，受 RAM、页面文件及系统限制影响；它不等同于任务管理器中的当前物理驻留量。

首次故障附近，物理 RAM 尚有数 GiB 可用，但系统已提交约 39 GiB，接近当时的 39.115 GiB 上限。**仍有空闲 RAM，不代表系统一定能接受新的提交申请。**

游戏错误发生后，自己的 CrashSight 采样也显示仍有约 4,697 MB 可用物理内存。该采样处于错误处理阶段，不能当成错误前精确同一时刻；但它与“不是简单的物理 RAM 全部耗尽”的判断一致。

重试时情况更差：游戏记录的 AvailablePhysical 只剩约 604/754 MiB，说明之后物理余量与提交余量同时紧张。

### 4.2 不支持“独显物理显存用满”的简单解释

首次错误时游戏记录预算 15,416.53 MB、使用 6,864.32 MB。适配器传感器同一阶段也显示 RX 9070 XT 专用显存仍有约 6.3 GiB 空闲。

所以最符合数据的是：**系统整体内存/提交压力影响了 D3D12 资源申请，最终由游戏统一报成 video memory 错误。**

仍需保留边界：没有捕获失败 CreateHeap 的完整描述、WDDM 分配明细和符号化堆栈，因此不能完全排除特定堆需求、碎片化或驱动分配问题。预算未用满不是“所有图形分配必然成功”的保证。

游戏日志中高达约 128 TiB 的 `AvailableVirtual` 是虚拟地址空间口径，不是可用 RAM 或可提交容量，不能据此否定内存耗尽。

## 5. 能否认定为游戏内存泄漏？

### 已证实

- 游戏当时是 Windows 2004 列出的最大单进程提交者，达到 **14.853 GiB**。
- 退出后旧 PID 在两次事件中仍各有 **8.380 GiB** 提交记账。
- 重试的新实例又增加约 5.920 / 7.072 GiB，旧新叠加与失败同窗发生。
- 游戏确有 D3D12 和普通内存申请失败，而非只显示一个泛化提示。

### 尚未证实

- **14.853 GiB 并不自动等于泄漏。** 可能包含正常工作集之外的缓存、保留/提交、加载期资源，也可能存在泄漏。
- **旧 PID 记账未消失不自动等于它仍在正常运行。** 后续事件中该项句柄数为 0，可能处于退出/清理过程；不能简单称为“两份完整游戏同时运行”。
- 没有进程级连续 Private Bytes 曲线、可比场景下多轮稳定基线，不能证明它每局净增长且不回落。
- 没有分配栈或完整内存快照，不能归因某个 Lua UI、纹理池、ACE 模块或显卡驱动。

本次重算系统 commit 分钟统计：21:08–21:26 大多在约 38.0–38.6 GiB 摆动，21:28–21:29 一度回落到约 36.0 GiB，随后再次升高。**这不是一条足以独立证明持续泄漏的单调增长曲线**；系统总量也不能替代游戏进程自身曲线。

游戏日志能把观察窗口向前扩展到 19:12，但已提取的日志没有提供完整、可比较的逐局私有提交序列。首次加载的低内存值与进游戏后的高值相比较，同样不能直接证明泄漏。

因此当前更准确的标签是：**已确认 OOM；高提交压力与退出后旧 PID 记账残留是重点，持续泄漏及其具体代码源仍待定位。**

## 6. CrashScope 是否导致了这次故障？

**没有证据把 CrashScope 定为主要内存占用源，也不能把其影响判为零。**

- Windows 首次 2004 中，游戏为 14.853 GiB，第三名 Explorer 约 0.663 GiB；CrashScope 未被列入前三名。该事件没有给出它的精确用量，也不能覆盖它引起的所有内核/驱动开销。
- 旧版 0.9.2 DxgKrnl 收到了 **191,614,618** 个事件，约 13.8 万/秒，而匹配和持久化事件为零。这是明显不值得保留的高流量路径，确实可能增加 CPU、临时分配和系统缓冲开销。
- 故障时只剩几 MiB 提交余量，额外开销可能让已经贴线的系统更早失败，但无法从现有记录计算“没有 CrashScope 就会不会闪退”。
- 旧会话没有后来新增的自身开销连续指标。P1 的短时 Smoke 进程数字不能拿来反推旧 Desktop 当时的真实内存。

所以应继续保持新版本 DxgKrnl 默认关闭，避免再用旧全功能采集包与反作弊游戏同跑。不能因此宣称当前版本已获得游戏兼容性保证。

## 7. 原因分级

| 判断 | 证据等级 |
|---|---|
| 三角洲发生真实内存分配失败，首次为 D3D12 CreateHeap E_OUTOFMEMORY | 直接证据，已确认 |
| 系统提交容量被游戏与其余系统/后台需求推到上限 | Windows 2004 + CrashScope + 游戏 AvailablePageFile 相互支持 |
| 首次渲染分配失败主要受系统提交压力影响，而非简单显存容量满 | 强支持的机制解释，未获得底层分配全信息 |
| 旧 PID 记账残留与新实例重叠促成后续重试失败 | 直接记账证据与 OOM 日志吻合；残留机制未知 |
| 游戏或图形/退出清理链存在泄漏 | 候选方向，尚未确诊 |
| 某个 Lua UI、ACE、GameViewer、驱动版本就是泄漏源 | 证据不足，不作此归因 |
| CrashScope 自身泄漏是主因 | 现有证据不支持；边际开销仍可能促成触顶 |

## 8. 建议处理顺序

### 先避免重复事故

1. 正常重启系统后再试，避免在旧实例资源尚未清理时连续重开。重新进入前观察任务管理器中的游戏实例与系统“已提交”是否回到合理基线。
2. 游戏前关闭不必要的开发工具、浏览器、WebView 宿主和录制/覆盖层；不要只按进程数量判断内存大小，应看提交量。
3. 保持页面文件启用，检查所在 SSD 的可用空间和系统管理策略。是否扩大应结合实际磁盘余量决定；本轮没有改设置，也不能用重启后的页面文件大小推断事故时的配置上限。
4. 不要将“清理待机内存”当成修复私有提交泄漏的方法；不建议禁用 ACE、强杀内核驱动或反复制造 OOM。
5. 保留当晚三份游戏日志和 Windows 2004 XML，再通过游戏官方渠道提交问题。普通更新/文件校验是低风险排查项，但现有日志不能证明文件损坏或特定版本必然有泄漏。

### 真正区分“容量不够”和“持续泄漏”所需的最小补测

在干净启动、确认游戏兼容的观测方式下，每隔 10–30 秒记录：

- 系统 CommitBytes / CommitLimit；
- 游戏 PID + 创建时间 + Private Bytes/Commit Size + Working Set；
- 正常退出前后及等待一段时间后的变化；
- 同一场景/相近负载每一局回大厅后的稳定基线；
- CrashScope 如参与观测，其自身开销也必须独立记录。

若多次可比场景结束后游戏 Private Bytes 基线持续抬高，且没有随卸载回落，才更支持持续泄漏；若旧 PID 消失后系统提交仍长期不回落，则需进一步查驱动/内核资源或其它进程，不能继续把旧 PID 记账当作完整解释。

不建议为了定位泄漏直接向运行中的 ACE 游戏附加调试器或做进程内存转储；需要分配栈级定位时，应使用游戏官方支持的诊断方式。在提交比例已达 90–95% 时就停止测试并正常退出，不必再逼近 100%。
