#### 内存事故主结论再次得到数据支持

五秒 memory-pressure 流峰值 **99.922485%**；一秒遥测的 Virtual Memory Load 峰值 **99.98847%**。两个数来自不同采样流，不混成同一个精度口径。

本次重新查询原始 Windows 2004 XML，记录 ID 10965、10979、10992 的系统 commit charge/limit 及有效 top-process commit 数值，与历史导出一致：

| 时间 | 系统提交/上限 | 关键游戏进程提交记账 |
|---|---|---|
| 21:30:48 | 39.022 / 39.115 GiB | 旧 PID 11248：14.853 GiB |
| 21:32:13 | 38.866 / 39.115 GiB | 旧 PID 11248：8.380 GiB；新 PID 33844：5.920 GiB |
| 21:34:50 | 39.022 / 39.115 GiB | 旧 PID 11248：8.380 GiB；新 PID 36452：7.072 GiB |

因此“严重系统提交压力 + 旧 PID 记账与新实例重叠”有直接证据支持。**仍不能据此确定旧 PID 残留属于应用泄漏、退出清理延迟、驱动引用还是终止过程中的记账语义。**

同一会话采到的独显温度峰值为核心 55°C、显存 68°C、热点 78°C；本段记录没有显示显著过热。磁盘读延迟峰值约 16.26 ms、写延迟峰值约 0.54 ms，不支持把持续磁盘高延迟当作这段故障的主要解释；这些不是对未采到瞬间的排除证明。

#### 覆盖边界

- 录制开始时游戏已运行，不能从本段推导完整冷启动内存增长曲线。
- CrashScope 21:31:30 停止；后两次重试依赖 Windows 事件补齐，不是同一段连续 recorder 数据覆盖的完整重启周期。
- DxgKrnl health 记录收到 191,614,618 个事件，但 matched/written 均为 0；不能把高事件量当成有效故障事件覆盖。
- Power 为 PermissionDenied；WHEA 即便 Started 也无持久事件；管理员有效 ETW 覆盖仍未验证。
- 该版本早于 P0/P1 降载加固。它在高压力下采样稳定，不等于后加的 95/98% 策略已经实机触发验证。

## 4. 发现并修正一处旧分析遗漏

旧报告 `docs/mcp-session-deep-analysis-20260918.md` 将 DWM 文件当成缺失，并统计 14 个 JSONL / 3,016 条。

实际会话里存在：

- `dwm-state.jsonl`，168 bytes。
- 1 条记录，时间 `2026-09-18T21:08:24.5725149+08:00`。
- `isCompositionEnabled=true`，description 为启动 baseline。
- SHA-256：`d94deffe81594c58fa6f0a0d01cf3d7715b5e89cbb5ad0b41a95e38ab7553135`，与当时 source-manifest 完全一致。

根因可定位到 `.mcp-probes/deep-analysis-20260919/analyze-session.ps1:68-72`：固定 `$jsonlNames` 清单漏了 `dwm-state.jsonl`。并非本轮新增了历史记录，也不是原文件后来变了。

**更正后的判断**：0.9.2 已观测到一次“合成开启”基线，不能再把这段数据的 DWM baseline 记作缺失；全量是 **15 个 JSONL 文件、3,017 条记录**。但合成开启不等于独立测得硬件渲染，且不证明整段没有瞬时回退。

P1 把 baseline 提前到初始化并增加健康/HRESULT 表达仍有价值，但不能将其描述成这台机器上从“从未有过 DWM 基线”到“首次有基线”的修复。

本次保留旧报告、旧脚本、旧分析结果不改写，通过本节明确勘误，避免破坏原有审计轨迹。
