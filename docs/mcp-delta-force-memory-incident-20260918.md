# 三角洲“内存不足”事件诊断

日期：2026-09-19（UTC+8）

## 结论

截图报错及其后的 ACE 提示都有完整记录支撑。这是两个连续阶段：先由 **Windows 提交内存（commit / 虚拟内存）耗尽** 导致三角洲退出；随后一次非正常重启使 ACE 反作弊预启动进入静默模式，ACE 明确要求再次重启后才允许恢复正常游戏流程。主要内存占用者是 `DeltaForceClient-Win64-Shipping.exe`；不是独显物理显存耗尽，也不是 GPU 过热。

游戏弹窗写“可使用的物理内存不足”，但故障时物理 RAM 尚有约 3–5 GiB 可用。真正接近零的是提交余量：CrashScope 一秒遥测最低只剩约 0.005 GiB，Windows 同时连续写入 Resource-Exhaustion-Detector 事件 2004，明确诊断“虚拟内存不足”。

本次没有证据表明 CrashScope 是主因。录制器在 21:31:30 正常停止，桌面端在 21:33:18 以代码 0 退出；21:34:50 Windows 仍记录由两个三角洲进程主导的内存不足。

## 关键证据

### 1. 提交内存长期贴顶

`memory-pressure.jsonl` 的 278 个五秒样本显示：

- 首样本 21:08:24 已提交 38.002 GiB / 上限 38.945 GiB，即 97.58%。
- 250 个样本达到或超过 95%，183 个达到或超过 98%，29 个达到或超过 99%。
- 21:31:14 达到 99.922%，五秒采样口径下仅余 31.05 MiB 提交空间。
- 一秒 `telemetry.jsonl` 的 Virtual Memory 传感器峰值为 99.988%，最低可用值约 0.005 GiB。
- 21:31:19–21:31:24 提交量骤降 6.292 GiB，从 99.922% 降至 83.836%，与游戏从采集记录中消失的时间一致。

物理 RAM 并未同时耗尽：

- RAM 使用峰值约 20.017 GiB。
- RAM 最低可用约 3.098 GiB。
- 因此这是“仍有物理空闲，但系统无法再承诺新的提交内存”的典型提交上限问题。

### 2. Windows 明确归因三角洲

System 日志的 `Microsoft-Windows-Resource-Exhaustion-Detector` 事件 2004：

| 时间 | 主要虚拟内存占用者 |
|---|---|
| 21:30:48 | 三角洲 PID 11248：15,948,550,144 B（14.853 GiB）；`msedgewebview2`：1.044 GiB；Explorer：0.663 GiB |
| 21:32:13 | 三角洲 PID 11248：8.380 GiB；三角洲 PID 33844：5.920 GiB；`msedgewebview2`：1.058 GiB |
| 21:34:50 | 三角洲 PID 11248：8.380 GiB；三角洲 PID 36452：7.072 GiB；Explorer：0.662 GiB |

21:32 和 21:34 同时存在两个 `DeltaForceClient-Win64-Shipping.exe` PID。记录不能单独说明这是正常多进程模型、重启重叠还是旧实例未释放，但它直接解释了重新尝试后仍然触发内存不足。

### 3. 独显显存和温度均未到危险区

RX 9070 XT 的适配器级传感器：

- GPU Memory Total：16,304 MiB。
- D3D Dedicated Memory Used 峰值：9,733 MiB。
- D3D Dedicated Memory Free 最低：6,455 MiB。
- GPU 核心温度峰值：55°C。
- GPU 显存温度峰值：68°C。

进程级 GPU 记账显示三角洲 dedicated 峰值约 6.744 GiB、`GameViewerServer` 约 7.706 GiB；这些进程计数器可能重叠或跨适配器聚合，不能相加后当作物理显存使用量。适配器级传感器仍有约 6.3 GiB 空闲，因此不支持“爆显存”结论。

### 4. 退出和重启时间线

- 21:31:19：最后一次捕获三角洲 PID 11248 的 GPU 记账。
- 21:31:22：前台从游戏切到 `browser`。
- 21:31:24：系统提交量释放约 6.292 GiB。
- 21:31:30：CrashScope 录制器写入 clean shutdown。
- 21:33:18：CrashScope Desktop 正常退出，代码 0。
- 21:34:50：CrashScope 已退出后，Windows 再次报告两个三角洲 PID 导致虚拟内存不足。
- 21:37:16：用户通过开始菜单发起第一次重启；21:37:38 事件日志正常停止，21:37:57 系统启动。
- 21:38:08–21:39:29：第一次重启后的系统又发生一次非正常重启。Kernel-Power 41 的 BugcheckCode 为 0，且该时间窗没有新转储文件；只能确认系统未正常关机，不能证明发生了蓝屏或由 ACE 导致崩溃。

### 5. ACE 后续提示和再次重启

用户补充的“后面触发 ACE、必须重启才能进游戏”与系统日志完全吻合：

- 21:31:22：三角洲第一次退出后，`ACE-CORE102706` 与 `ACE-CORE202706` 文件系统筛选器卸载。
- 21:31:38：两项 ACE 筛选器重新加载；21:33:00 再次卸载。
- 21:34:16：再次加载；21:35:30 再次卸载。这与连续重试游戏及多个三角洲 PID 的时间一致。
- 21:37:17：`SGuard64.exe` 尝试否决系统关机。
- 21:37:29：Windows 记录安装 `ACE-SSC-DRV64` 内核驱动，路径为 `C:/Program Files/AntiCheatExpert/SGuard/x64/plugins/ACE-SSC-DRV64.sys`。
- 21:40:44：非正常重启后的系统中，ACE 两项筛选器重新加载；21:40:56 再次安装 `ACE-SSC-DRV64`。
- **21:41:18：Windows Application Popup 完整记录 ACE 原文：**“由于电脑非正常关机（如断电、蓝屏），预启动处于静默模式。您需要重启电脑，以便重新进入‘腾讯游戏反作弊预启动模式’。（13-262426-0）”
- 21:41:31：用户按提示发起第二次正常重启；21:41:54 系统重新启动。
- 21:43:04：`ACE-BASE.sys` 和 `ACE-CORE302706.sys` 更新，ACE 筛选器重新加载；21:43:20 再次注册 `ACE-SSC-DRV64`。

因此后半段不是普通的内存弹窗重复，也没有证据表明 ACE 将 CrashScope 判为作弊工具。ACE 自己记录的拒绝原因是 **上一次系统非正常关机导致反作弊预启动模式失效**，所以必须再重启一次。完整故障链是：提交内存耗尽 → 三角洲退出/重复启动 → 第一次重启后又出现非正常重启 → ACE 进入静默模式并阻止正常进入 → 按 ACE 要求再次重启。

## 页面文件现状

2026-09-19 00:09 的只读查询结果：

- Windows 自动管理页面文件：开启。
- `C:/pagefile.sys` 当前分配 11,264 MiB。
- 当前总虚拟内存约 34.11 GiB。
- 故障会话中提交上限曾增长到约 39.115 GiB，说明自动页面文件已经扩展过，但总需求仍触顶。
- C 盘当前总计 128 GiB、空闲约 33.03 GiB（25.8%）。

所以问题不是页面文件被关闭，而是 24 GB 级 RAM、游戏高提交量和同时运行的开发/浏览器/WebView/通讯软件共同超过了当时约 39.1 GiB 的提交上限。

## 建议处置

1. 重启后先确认任务管理器中没有遗留或重复的 `DeltaForceClient-Win64-Shipping.exe`，再只启动一个游戏实例。
2. 玩游戏前关闭不需要的 ShunCode、浏览器/WebView、QQ、录屏与覆盖层；重点观察任务管理器“性能 → 内存 → 已提交”，而不只看“可用 RAM”。
3. 保持页面文件启用。C 盘只剩约 33 GiB，不建议盲目设置很大的固定页面文件；如需扩大，先规划磁盘空间或将可用页面文件放到空间充足的 SSD。
4. 若干净启动后单开游戏仍持续增长到提交上限，优先按游戏内存泄漏或重启残留排查：更新/验证游戏文件，临时关闭 Game Bar、录屏和第三方覆盖层，并记录每次出现第二个游戏 PID 的时间。
5. 长期同时运行开发栈与三角洲时，32 GB 只是较低改善目标；更稳妥应结合主板插槽和现有条规格评估 48 GB。升级前先确认重复进程问题，避免用加内存掩盖异常增长。

## CrashScope 后续改进点

本次采集成功证明系统级提交压力和 GPU 适配器状态，但进程快照目前只记录 PID/名称，最终进程归因依赖 Windows 事件 2004。后续建议：

- 在进程快照中增加 Private Bytes、Commit Size、Working Set 与启动时间。
- 捕获并关联 Resource-Exhaustion-Detector 事件 2004。
- 对提交占比 90%/95%/98% 分级告警，并明确区分 RAM、commit 和 VRAM。
- 检测同名游戏进程重叠及 PID 代际，避免把多个实例合并为单一进程趋势。
- 事件导出中同时保存页面文件配置、提交上限与磁盘可扩展空间。
