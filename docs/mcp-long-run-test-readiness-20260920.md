# 四小时长时测试停止前回顾

日期：2026-09-20（UTC+8）
状态：等待当前长时测试自然结束，尚未读取本次测试的最终数据。

## 1. 回顾结论

现有记录显示，2–4 小时常驻稳定性一直是 CrashScope 的开放验收项。本次正在进行的长时测试应作为对该缺口的补测；在最终数据落盘并完成收尾检查前，不把它判定为通过或失败。

已有历史实测不应归零：0.9.1 做过基础 GUI、录制、页面往返和 Stop/Start；0.9.2 有约 23 分钟真实游戏负载数据；P1 smoke 已证明部分新增指标能在真实机器产生并正常收尾。但这些记录不能替代当前候选包的四小时 Desktop 长时验收。

## 2. 本次长测要回答的问题

1. 录制器是否能在长时间运行中持续产出采样，是否存在静默间隙、采样频率漂移或错误后无提示停止。
2. CrashScope 自身的 Private Bytes、Working Set、CPU、句柄和线程是否呈持续上升趋势。
3. ETW 速率、丢失计数、采集健康、GPU/DWM、页面文件和资源压力状态是否稳定，是否出现误报或未解释的状态跃迁。
4. 会话文件、日志和 telemetry 是否持续增长但保持可读，是否出现重复写入、截断、锁未释放或数据目录异常膨胀。
5. 用户执行 Stop 后是否得到真实的正常收尾：状态、journal、cleanShutdown、recorderError、lastSampleAt 和最终样本彼此一致。

## 3. 停止后优先保留的数据

停止后不要立即清理、覆盖或重新启动同一数据根。至少保留：

- 测试包版本、构建身份、提交或工作树标识；
- 测试开始和结束的本地时间、实际持续时长、session ID；
- 会话目录完整副本及文件清单/大小；
- `telemetry.jsonl`、`collector-health.json`、`collector-overhead.jsonl`、`process-snapshots.jsonl`；
- `memory-pressure.jsonl`、`pagefile.jsonl`、`dwm-state.jsonl`、`gpu-engines.jsonl`、`gpu-memory.jsonl`、`storage.jsonl`；
- journal、状态文件、错误日志和停止后的最后状态；
- 若有异常，保留对应时间点前后至少数分钟的原始记录，不只提供截图或汇总数字。

## 4. 收数后的判定顺序

先核对时间范围、session 身份和文件完整性，再统计样本数、首末时间、缺口、错误、丢失和文件增长。随后比较开始、中段、结束的进程资源快照，最后检查正常停止语义和异常事件关联。

四小时稳定运行可以支持“本次场景下长时运行未观察到故障”，但不能单独证明不存在内存泄漏、不能证明反作弊游戏兼容，也不能把系统提交量变化归因给 CrashScope。若发现 Private Bytes 或系统提交上升，需结合进程级曲线、旧 PID、游戏进程和事件时间线区分容量压力、残留记账与持续泄漏。

## 5. 已知解释边界

- 当前评审已指出 DWM 启动 baseline 可能被误判为软件渲染回退，收数时要区分 baseline 与实际从开启到关闭的转换。
- 历史 P1 smoke 不是完整 WPF Desktop 的开销基线；不能用它替代本次长测的进程资源曲线。
- 旧记录中的 `desktopGuiSmokeExecuted=false` 只说明旧发布包验证未覆盖该路径，不代表本次长测结果；本次应以实际候选包和本次会话产物为准。

## 6. 停止后的分析规划

分析分为四轮：

1. **证据冻结与完整性**：记录包版本、构建身份、session ID、起止时间；列出文件、大小、首末修改时间并计算哈希。先确认数据属于本次运行且没有被覆盖。
2. **生命周期与采样完整性**：读取 journal、最终状态、`collector-health.json` 和 `telemetry.jsonl`，核对首末时间、样本间隔、缺口、重复、解析错误、`cleanShutdown`、`recorderError` 和锁释放状态。
3. **趋势与关联**：对进程资源、采集器自身开销、ETW loss、内存压力、页面文件、GPU/DWM 和存储指标计算首段/中段/末段统计、每小时变化率和异常时间窗，再与错误、进程事件和停止时间对齐。
4. **判定与复核**：输出“本场景通过 / 有条件通过 / 未通过”，明确哪些是数据直接证明的事实、哪些只是风险信号、哪些仍需补测；不使用单个峰值直接宣称泄漏或兼容性结论。

## 7. 各类数据的作用

| 数据 | 主要作用 |
|---|---|
| `telemetry.jsonl` | 主时间线，确认采样是否连续、基础指标是否持续产生 |
| `collector-health.json`、journal、最终状态 | 判断采集器状态迁移、错误、正常停止和会话收尾 |
| `collector-overhead.jsonl` | 判断 CrashScope 自身 CPU、内存、句柄、线程等开销趋势 |
| `process-snapshots.jsonl` | 区分 CrashScope、游戏和旧 PID 的进程级资源变化，支持泄漏与残留记账分析 |
| `memory-pressure.jsonl`、`pagefile.jsonl` | 判断系统提交压力、阈值、降载或页面文件变化，避免把系统压力误归因给程序泄漏 |
| `gpu-engines.jsonl`、`gpu-memory.jsonl` | 判断 GPU 采集是否有效、adapter/engine 身份是否稳定以及 GPU 内存变化 |
| `dwm-state.jsonl` | 区分启动 baseline 与真实渲染回退，避免已知误报 |
| `storage.jsonl`、日志和文件清单 | 判断磁盘健康、写入异常、日志/数据增长率和文件完整性 |

长测的结论边界是“在本次机器、负载和版本下是否稳定运行”，不能单凭四小时数据证明不存在所有内存泄漏，也不能证明反作弊游戏兼容或强杀/断电恢复能力。
